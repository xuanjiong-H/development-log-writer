# Development Log Rules

## Source of Truth

日志只记录原始对话、工作记录或用户提供材料中能够确认的内容。

- 事实来源包括明确的需求、实际执行的命令、已修改的文件、真实报错、排查过程、验证结果和明确的需求变更。
- “建议”“计划”“准备”“后续可以做”表示计划或建议，不表示已完成。
- 没有来源支持的技术栈、接口、文件、性能指标、业务收益和个人成果不得补写。
- 无法确认的内容统一标注为“原始记录未明确”或放入待确认说明。

## Information Filtering

过滤以下内容：

- 客套话和重复确认。
- 重复的相同命令、相同错误和无变化的调试过程。
- 空白消息、无效指令和与技术开发无关的讨论。
- 不能帮助说明需求、实现、排查、验证或迭代的过程噪声。

保留以下内容：

- 能够说明个人实际操作的动作。
- 关键技术选型和选择理由。
- 影响实现结果的约束和决策。
- 有代表性的错误、定位路径和最终解决方式。
- 需求新增、删减、调整及其对实现的影响。
- 明确的验证结果和交付结果。

## Six Core Modules

### 1. 需求梳理

说明业务需求、基础要求、功能目标、核心问题和落地价值。区分原始需求与实现约束。

### 2. 技术方案

说明实际采用或明确讨论过的技术栈、开发思路、架构、方案选型原因和落地流程。没有明确采用结果时，标记为讨论方案。

### 3. 技术重点

提炼技术难点、关键技术点、选型取舍、复杂逻辑和难点解决方式。避免把普通 CRUD 或简单操作包装成技术亮点。

### 4. 代码处理

记录实际编码、接口编写、逻辑实现、代码重构、配置修改和功能落地。尽量保留具体文件、模块、函数或功能名称。

### 5. Bug 修复

按“问题表现 -> 排查思路 -> 根因 -> 修复方式 -> 验证结果”描述问题。没有完整链路时，只写能够被记录支持的部分。

### 6. 需求更新

记录新增功能、需求删减、细节调整、范围变化和对应的适配操作，说明变更对开发结果的影响。

## Resume Adaptation

- 使用专业书面表达，突出个人动作和技术结果。
- 重点技术点、核心实现和明确成果可以加粗。
- 只在原始记录有证据时使用“完成”“解决”“验证通过”等结果性表述。
- 不虚构百分比、性能提升、业务收益、用户规模或团队影响。
- 保留足够技术细节，使内容能够拆解为简历项目经历，但不要把全文压缩成空泛的简历 bullet。

## Quality Gate

生成前检查：

- 六个核心模块是否全部存在。
- 是否增加了个人工作复盘。
- 每个关键结论是否有原始记录依据。
- 是否区分已完成、失败尝试、计划和待确认事项。
- 是否删除了重复调试和无效对话。
- 是否仍然能够看出需求、方案、编码、问题和迭代之间的关系。
